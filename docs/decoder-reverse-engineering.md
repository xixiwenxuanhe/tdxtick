## 2. 已确定的事实（可信，勿重复推导）

### 2.1 网络帧结构

抓包点：`WS2_32!WSARecv` 完成（`kernel32!GetQueuedCompletionStatus` onLeave）。帧格式（校验：`i+16+len<=cap`）：

```
偏移 0..9    头（b1 cb 74 00 | 0c 0a 08 xx | xx 00）
偏移 10..11  命令码 u16 LE   ← 0x0550 / 0x0554 / 0x0547 / 0x0527 / 0x054c / 0x054e ...
偏移 12..13  载荷长度 u16 LE
偏移 14..15  同 12..13（重复）
偏移 16..    载荷
```

发送侧同理（调用点 `TdxAsioComm64.dll+0x7c92`）。

### 2.2 命令

| cmd | 含义 | 观察到的载荷 |
|---|---|---|
| `0x0550` | 定位/心跳 | 固定 12B = `00 00 "000759" <u32 递增序列>` |
| `0x0554` | **逐笔数据流（目标）** | 变长 34–175B 的增量编码 |
| `0x0547` / `0x0527` | 行情/分时相关 | 变化中的小结构 |
| `0x054c` | 批量股票代码列表 | 明文可读 |
| `0x054e` | 其它 | — |

### 2.3 0x0554 载荷特征

- 非 zlib / raw-deflate / gzip / bz2 / lzma（全试过）。
- 信息熵 **5.88 bit/byte**（结构化，不是压缩/加密）。
- 字节 `0x5b` 占 13%、`0x49` 占 11%、`0x0a` 占 6.7%。
- 长度与记录数关系稳定：`len = 首条(21–22B) + (k-1)×~13B`；实测 `22 + 7×13 = 113` 精确吻合。
- **关键否定结果**：对单条记录，把字段值（时间/价/量/买委托号/卖委托号）按 u16/24/32、LE/BE、float32、×/÷100、÷10000 在载荷里暴力搜索 → **0 命中**。说明是**跨记录差分/熵编码**，字段不是明文。

### 2.4 解码后的记录（已知，用它做已知明文校验）

内存对象：`obj = rdi @ TdxW.exe+0x79bd0b`（成交列表渲染）。
- `code = [[obj+0x68]]`（6 字节 ASCII）
- `count = u32 @ obj+0x250`，`data = ptr @ obj+0x348`
- 记录 20B：`<HIIbBII>` = 秒、价×10000、手、零股、方向、买委托号、卖委托号
- 显示秒 = 字段秒 **+21600**（铁证：`TdxW.exe+0x798820` 里有 `add r9d,0x5460`，步长 `add r8,0x14`）

### 2.5 处理链（已定位）

```
收包: TdxAsioComm64.dll+0x9e80 (内部 call [rip+0x4e532] → WSARecv, 返回于 +0x9f2e)
  → 帧状态机: Viewthem64.dll+0x5db50  (把 [rbx+0x168] 的载荷 memcpy 到全局 Viewthem64+0x1E0090)
  → 按命令码分发 → 各数据模块
写"逐笔显示缓冲"的拷贝走 MSVCR100.dll 的 memcpy（不是 ntdll！）:
  TdxW.exe+0x54a685  ← +0x345382 ← +0x79f725 ← +0x7565ff(MFC UI)
  TdxW.exe+0x79f7a5  ← +0x7565ff
  TdxW.exe+0x799af3  ← +0x79f82a ← +0x7565ff
  TCalc64.dll+0x119b8 ← +0x45184 ← +0x4988f ← +0x4b22c ← +0x904f9 ← TdxW.exe+0x1ebc05 ← +0x1e538b ← +0x880a13 ← +0x87ea67 ← +0x75aec4(MFC)
```
→ 这些都是 **UI 线程把「已解码记录」搬进显示缓冲**；真正把 `0x0554` 载荷变成记录的**解码器在这条链更上游**，尚未钉死。

### 2.6 iOS 端符号（解密 IPA，可作对照）

`com.tdx.pushMessage_7.27_decrypted.ipa` → `Frameworks/TdxCore.framework/TdxCore`（Mach-O arm64，**保留 49207 符号**，可 capstone 反汇编）。
- 协议结构体名：`mp_tick_req` / `mp_tick_ans`（逐笔）、`mp_zst_req/ans`（走势/分时）、`mp_hqinfo`、`mp_pageall_ans` …
- `mp_tick_req` 大小 = **46B**；`mp_tick_ans` = 头 `0x27` + `count × 18B` 记录 + 120B attach info；原始记录在 `mp_pageall_ans+0xfc`。

> 注意：iOS 走 RPC，Windows 走 TCP 自定义编码，**线格式未必相同**，但字段语义可对照。

## 4. 建议的破解路线（按优先级）

1. **已知明文 + 差分建模**（不需要实时进程，用 `probe/pairs/` 已有样本即可）：

   - 重点：首条 vs 后续 ~13B 的差分；观察 `e5 0f`、`49`、`d1 5e`、`4b 49` 等高频字节是否是**域间分隔/游程标记**。
2. **定位解码器函数**（需盘中 + lab）：
   - 从 `TdxW.exe+0x880a13 / +0x87ea67`（疑似网络消息分发）向上/向下追。
   - 或在 `TdxAsioComm64` 的分发回调里，对「收到 0x0554 后的调用序列」用 Stalker（注意：跟 GQCS 线程抓不到，可能在其他线程）。
   - 或对 `Viewthem64+0x1E0090` 之后被读取的缓冲找到真正的解码输入。
3. **参考实现**：开源 `pytdx` 里有 TDX 分笔协议实现，可对照其「解压/位打包」思路（命令码不同，但风格可能一致）。

## 5. 已知坑

- 钩 `ntdll` 的 memcpy **无效**——TDX 用 `MSVCR100.dll` 的 CRT 拷贝。
- `MemoryAccessMonitor` 的 `Thread.backtrace()` 返回的是 Frida 自身栈，**不可用**；只能用 `from`（模块+偏移）。
- 不要在 `ntdll` 函数**内部地址**下钩（会把客户端钩崩）。
- 多开实例时，账户的 L2 逐笔订阅可能被抢占，导致部分实例「逐笔成交为空」——这与本任务无关。
- Stalker 跟 `GetQueuedCompletionStatus` 所在线程抓不到解码（解码可能在别的线程）。

## 7. 附加发现（差分记录结构，2026-09-11 13:2x）

用「首条 21B + 之后每条 13B」切分 0x0554 载荷后，结构清晰（`probe/pairs/` 样本）：

```
k=5, len=73, first=21
chunk0(21B): 4c 49 6f aa 4b 49 ca 2e e9 f0 43 5b 49 f6 ef cb 50 e7 eb be 51
chunk1(13B): ca 2e 49 4a 49 f6 ef cb 50 c6 8e c8 50   bid=26233279 ask=26227151 sh=300
chunk2(13B): ca 2e 49 48 49 f6 ef cb 50 e1 e8 cb 50   bid=26233279 ask=26232936 sh=100
chunk3(13B): ca 2e 49 47 49 c2 e3 cb 50 e1 e8 cb 50   bid=26233483 ask=26232936 sh=1400
chunk4(13B): ca 2e 49 4f 49 c2 e3 cb 50 e0 e8 cb 50   bid=26233483 ask=26232937 sh=600
```

对应关系（**已用多组样本验证**）：
- 13B 块 = `前缀(5B: ca 2e 49 XX 49)` + `bid(4B)` + `ask(4B)`。
- bid 变 → 第 6..9 字节变；ask 变 → 第 10..13 字节变；不变则字节不变。
- 前缀里 `ca 2e` 在首条里出现在偏移 6；`XX`（第 4 字节）随记录变化（疑似 volume/方向）。
- `49` 高频出现在固定位置，疑似字段标记。

**仍未解出**：bid/ask 这 4 字节到订单号的变换。已知：
- 不是明文 u16/24/32、也不是 float32（float32 在 1.3e9 处分辨率 128，无法表示观察到的 ±1 变化）。
- `ask=26232936 → e1 e8 cb 50`、`ask=26232937 → e0 e8 cb 50`（低字节 −1），但仍需找到完整变换。
- 疑似「浮点定点」或「分段/比特打包」；建议对 chunk 按**位（bit）**而非字节做暴力对齐，用 bid/ask 的已知值做约束。

样本目录：`probe/pairs/`（`w_<t>_0554_<len>.bin` 线数据、`b_<t>_<from>_<to>.bin` 20B 解码记录）。

## 8. 更新（2026-09-11 下午，多路尝试后）

### 8.1 已经排除的假设（不用再试）

对 22 组干净样本（同一 payload 内 delta 记录的 bid 4 字节 ↔ 内存订单号）验证：

- 明文整数 u16/u24/u32、float32（LE/BE）、×/÷100/1000/10000 —— **0 命中**。
- 256 种字节置换 —— **无一单调**，且不存在位级一一对应（order 的任一位 ≠ enc 的任一位，含取反）。

- 关键反例（同一 payload 内，`first=21`，已交叉核对）：
  ```
  bid 26233279 -> f6 ef cb 50   (0x50CBEFF6)
  bid 26233483 -> c2 e3 cb 50   (0x50CBE3C2)   # 值更大，编码更小 => 非单调

  ⇒ 这 4 字节**不是**订单号的单调数值编码。疑似：自定义浮点/定点（尾数打乱）、或与其它字段位交织、或按“变化量”编码。

## 9. 【关键突破】字段是变长编码（2026-09-11 14:1x）

### 9.1 决定性观察

在多条记录的 delta 流里，相邻记录的「bid 4 字节」是**整体右移 1 字节的滑动窗口**（000001）：

```
order        bytes
31582929     d8 e2 c6 57
...
31780822     69 a8 3b 49
31781133     af 69 a8 3b     <- 右移 1 字节
31793601     a7 af 69 a8
31804303     f1 a7 af 69
31839134     57 f1 a7 af
31844589     e6 57 f1 a7
31846003     f0 e6 57 f1
```

⇒ **记录不是定长 13B，字段也不是固定 4B 偏移**；是**变长（varint/位打包）字节流**。
之前所有「按固定偏移取 4 字节当订单号」的分析都建立在此误判上 —— §8 里"非单调"的结论作废（那是窗口错位造成的）。

### 9.2 单条记录（len=21）的布局是稳定的

000001 的 6 个单记录样本，位置完全一致：

```
48 49 [b2] 42 48 49 [b6] 3b e9 e4 47 [b11] 49 [b13 b14 b15] 69 ec a1 9f 69
```
- `48 49` 固定前缀；末 4 字节 `ec a1 9f 69` 对应 **ask**（这些样本 ask 全相同）。
- bid 在 `[b13..]` 附近；`69` 是最高字节（000001），000759 同位置是 `50` —— 最高字节随订单号量级单调。
- 注意：这些"4 字节"很可能仍不是字段边界，而是**变长字段在固定前缀后的自然落点**。

### 9.3 下一步（重要）

1. **按变长流解析**：对 1 条记录载荷，假设 `[前缀][varint...]`，用「同股票 + 已知 ask 恒定」的样本先把 `ec a1 9f 69` 段定死。
2. **对齐 delta 块**：多条记录时，用「相邻记录字节流是整体滑动」这一点，反推每条记录的**变长字段长度**（记录长度 = 各字段 varint 长度之和）。
3. 猜测：每字段是 **LEB128 变长整数（绝对值或增量）**；`0x49`/`0x69`/`0x50` 等高频字节是 varint 的终止/高位字节。

### 9.4 数据

`probe/pairs/`（本批 000001，主实例 PID 23124 采集）。每个 `len=21` 的 `w_*_0554_21.bin` 配一个 `b_*` 单记录，适合逐字段对齐。

### 9.5 单记录字节位置 ↔ 字段 相关性（000001，13 样本）

按「两样本该字段相等 ⟺ 该字节相等」判定的严格相关：

```
byte 0 = 48   CONSTANT
byte 1 = 49   CONSTANT
byte 2        ← time(秒) 与 bid（本样本集里两者同变，无法区分）   [0x66/0x62/0x64/0x79/0x67/0x7c/0x32]
byte 3 = 42   CONSTANT
byte 4 = 48   CONSTANT
byte 5 = 49   CONSTANT
byte 6        ← time 与 bid                                          [0x8b/0xf4/0x89/0x8e/0x88/0x82/0x95]
byte 7 = 3b   CONSTANT
byte 8        ← px / dir                                             [0xe9 / 0xf5]
byte 9        ← px / dir                                             [0xe4 / 0xe2]
byte10 = 47   CONSTANT
byte11        ← 成交量 sh                                            [0x4a/0x4d/0x48/0x43/0x40/0x4b]
byte12        ← px / dir                                             [0x49 / 0xc9]
byte13        ← (bid 低段)
byte14        ← time / bid
byte15,byte16 ← (bid 高段)
byte17        ← px / dir     (! 不是 ask)
byte18,19,20  ← ask
```

要点：
- `px=11.75 ⟺ dir=1`、`px=11.76 ⟺ dir=0`（本集内完全共变），所以 byte8/9/12/17 同时跟 px 和 dir。
- **成交量被单字节（byte11）编码**，但取值非单调（sh 100→0x48, 300→0x4a, 400→0x4d, 1000→0x43）⇒ **很可能是"变化量"或查表/位域**，而不是明文。
- 结论：**record = 固定 21B 布局 + 位打包字段**；delta 记录 = 变长。下一步应该按**位**解析这 21B（工具：用 `probe/pairs/` 的 13 个单记录样本做约束，搜索字段位宽与对齐）。

## 10. 干净配对 + 首条记录逐字节字段图（2026-09-11 14:1x）

**关键方法**：`probe/pairs.py` 单次采集时，0x0554 帧数与缓冲增量数 **严格 1:1**（本次 72:72），按时间/`from` 顺序配对即可。过滤条件：`len == first + 13×(nrec-1)` 且 `first∈{21,22}`。

### 10.1 首条记录（21B）逐字节字段相关（000759，38 组干净样本）

byte 3 : CONST 0x75
byte 4 : CONST 0x4a

### 10.2 delta 记录 = 复用上一条未变字段

r1                89 3a 49 53 49 e4 b1 ae 57 c9 b4 98 57              (13B, 增量)
```
`r1` 的末 6 字节 = `r0` 的末 6 字节（`ae 57 c9 b4 98 57`），前 2 字节 = `r0` 的第 6-7 字节（`89 3a`）。
⇒ delta 记录**只重发变化的字段**，未变字段由解码器沿用上一条 —— 这正是「变长 + 滑动窗口」的来源。

### 10.3 下一步（可执行的收尾）

1. 取**连续流**（本目录 72 帧按序拼接）与**连续记录流**（`b_*` 按 `from` 拼接，已验证时间单调），
   逐记录算出 6 个字段的差分 `(dt, dpx, dsh, ddir, dbid, dask)`。
2. 在字节流里定位这些差分（大概率是 **zigzag + varint**）：先看「差分=0」是否对应某个固定终止字节（如 `0x49`/`0x3a`）。
3. 用 `sh` 单字节非单调的事实锚定：先只在「其它字段不变、仅 sh 变」的记录里解 sh 的编码，再推广。

## 11. 【决定性突破】是 XOR 混淆，不是熵编码（2026-09-11 14:2x）

**结论先说：0x0554 是「明文 ⊕ 逐位置密钥」的简单混淆。已破解 3 个字段并逐样本验证。**

### 11.1 已验证的字段公式（首条 21B 记录，000759，38 样本 100% 吻合）

```
byte6  = (time_raw & 0xFF) XOR 0x49
         # 例 raw=0x73C2 -> 0xC2^0x49=0x8B ✓  (raw 就是内存记录的“秒”字段)
byte11 = 0x40 | (lots XOR 9)          # lots = 成交量/100
         # 100->0x48 200->0x4b 300->0x4a 400->0x4d 900->0x40 1000->0x43 2200->0x5f 全部 ✓
byte12 = 0x49 | (dir << 7)            # dir=0->0x49, dir=1->0xC9
```

### 11.2 bid/ask 也已指向 XOR

`bid XOR u32(b13:b17)` 与 `ask XOR u32(b17:b21)` 的**高字节恒为 0x56**（38 样本）：
```
bid=32311354 enc=0x57a1e9f3  -> 0x564ce1c9
bid=32312847 enc=0x57a1f1c6  -> 0x564cffc9
ask=32168863 enc=0x579fa7d6  -> 0x56757c49
...
```
高位一致 ⇒ 高位是 `order_high XOR 0x56`；低位还需定清是「低 16 位明文」还是「另一个子字段」。

### 11.3 待解（用同一套方法）

| 字段 | 位置（首条记录） | 状态 |
|---|---|---|
| time | byte6 | ✅ `(raw&0xFF)^0x49` |
| lots | byte11 | ✅ `0x40|(lots^9)` |
| dir | byte12 | ✅ `0x49|(dir<<7)` |
| price | byte8,9（+byte7=0x3a, byte10=0x43） | ⏳ 疑似定点/float16，需再拟合 |
| bid | byte13..16 | ⏳ 高位=`bid_hi^0x56`，低位待定 |
| ask | byte17..20 | ⏳ 同上 |

### 11.4 delta 记录

后续 13B 记录 = 同样的「字段 ⊕ 密钥」，且**未变字段沿用上一条**（字节与上一条尾部重叠）。解码时按「上次状态 + 本记录字段」重建。

### 11.5 下一步（很快能收尾）

1. 对 **price**：用「同一 payload 内只有 px 变化」的记录，拿 `(px, b8, b9, b7)` 做拟合；先试 `u16 = px/…` ⊕ 常数、或 float16 ⊕ 常数、或 Gray。
2. 对 **bid/ask**：先只看「低 16 位」是否满足 `u16_le(b13,b14) = (bid & 0xFFFF) XOR K`。
3. 三个已知字段(`time/lots/dir`)已可作锚点，锁定记录长度与字段边界。

## 12. 【收官进展】整条记录 XOR 0x49 后明文结构完全清晰（2026-09-11 14:3x）

### 12.1 密钥就是 0x49（重复）

之前的三个公式其实是同一个密钥：
```
byte6-7 : time(u16 LE)  = 明文 XOR 0x4949
byte11  : lots          = 明文 XOR 0x49
byte12  : dir           = 明文 XOR 0x49
```
把**整条记录每个字节都 XOR 0x49**，立刻得到规整明文。

### 12.2 明文记录布局（已由多条样本验证）

```
首条记录(21B):  [头6B]  time(2,LE)  price(2)  flag(1)  lots(1)  dir(1)  bid(4,LE)  ask(4,LE)
delta 记录(13B):          time(2,LE)            flag(1)  lots(1)  dir(1)  bid(4,LE)  ask(4,LE)
```
- `time` = u16LE@6（XOR 后）= 内存记录的时间秒（如 0x73C2=29634）✓
- `lots` = sh/100，`dir` = 0/1 ✓
- delta 记录**省略了 price（未变）**，所以是 13B；首条含 price 是 21B。

### 12.3 明文示例

```
CT: 4a 49 5c 75 4a 49 8b 3a d1 86 43 48 49 f3 e9 a1 57 d6 a7 9f 57
PT: 03 00 15 3c 03 00 c2 73 98 cf 0a 01 00 ba a0 e8 1e 9f ee d6 1e
     └─头6B──┘  time=29634  price?  f  lots=1 dir bid      ask
```
- PT[6:8] = `c2 73` → u16LE = 29634 ✓
- PT[11] = `01` → lots ✓ ; PT[12] = `00` → dir ✓
- `bid` = u32LE(PT[13:17]) 随 bid 单调；但 ≈ order×16.05，疑似**定点/浮点**（非简单 XOR/线性）。

### 12.4 还剩的字段格式（下一步）

| 字段 | 位置(Pt) | 已知 | 待定 |
|---|---|---|---|
| time | [6:8] | ✅ u16LE | — |
| lots | [11] | ✅ | — |
| dir | [12] | ✅ | — |
| price | [8:10]（首条） | px=87000→`98 cf`；87100→`bc d0`；87200→? | 2B 编码（疑似定点/float16） |
| flag | [10]（首条）/ [2]（delta） | 首条=0x0a，delta=0x00 | 含义 |
| bid | [13:17] | 随 bid 单调，≈order×16.05 | 定点/浮点格式 |
| ask | [17:21] | 同 bid | 同 bid |

**关键简化**：`bid`/`ask` 的明文单调 ⇒ 只要拟合出「明文 32 位 ↔ 订单号」的定点/浮点关系即可；`price` 只看 2 字节。

### 12.5 结论

**0x0554 已基本拿下**：帧结构 + 逐记录字段布局 + 密钥(0x49) + 3 个字段完全解出。
剩余只是 `price`(2B)、`bid`/`ask`(各 4B) 的**定点/浮点数格式**，用现有 38+ 样本做最小二乘/浮点拟合即可收尾。

## 9. 新增结论：0x0554 的变长整数层（2026-09-11 14:xx）

对同一响应内的记录逐字节按 TDX 公共协议的有符号变长整数解析后，原先“4 字节订单号块非单调/疑似浮点”的判断已撤销。线格式首先是变长整数层，不能按固定 13B 切片：

```text
首字节：bit7=1 表示继续，bit6=1 表示负数，低 6 位为数据
后续字节：bit7=1 表示继续，低 7 位为数据
数据按低位到高位拼接；首字节 bit6 只负责符号
```

解析后的值个数稳定为 `5 个流/头部值 + 6 个首记录值 + (记录数-1)×6`。因此 21/22 字节首块和后续约 13 字节块只是变长整数的字节表现，不能用字节长度定位记录边界。离线实现见 `probe/decoder0554.py`，测试见 `probe/test_decoder0554.py`。

在已配对的 `000759` 样本中，后续记录六个值的布局已经确认到以下程度：

```text
(time_code, price_code, lots_code, aux_code, bid_code, ask_code)
```

- 时间：`sec = abs(time_code) XOR 0x6c09`。样本 `26498 -> -2955`、`26499 -> -2954`、`26511 -> -2950` 交叉吻合。
- 手数：`lots = abs(lots_code) XOR 9`。例如 `-10 -> 3`、`-8 -> 1`、`-7 -> 14`。
- 买卖订单号：`order = abs(order_code) XOR 0x04993249`。例如 `f6 ef cb 50 -> -84507638 -> 26233279`，`e1 e8 cb 50 -> -84507169 -> 26232936`；买卖两侧和多个响应均吻合。
- `price_code` 在价格不变时为 `-9`，首记录价格仍使用独立的初始编码；`aux_code` 同时携带零股/方向状态，方向 0 的样本为 `-9`，方向 1 的样本观察到 `-4937`，其完整状态表尚未闭合。

`0x04993249`、`0x6c09` 和辅助字段状态目前只在 `000759` 会话样本上验证，不能直接假定对其它股票或新会话恒定。后续在线解码器应从首块/会话状态取得这些 key，并保留每个字段的原始变长整数，避免在 key 未确认时产生伪明文。

## 13. 【委托找到了】0x055e = 逐笔委托（2026-09-11 14:3x）

对 lab/主实例打开"逐笔委托明细"后抓包，得到**决定性的命令对称关系**：

| 数据 | 轮询/订阅 | 数据帧 | 已知 |
|---|---|---|---|
| 逐笔**成交** | `0x0550` | `0x0554` | 已解字段布局 |
| 逐笔**委托** | `0x0555` | **`0x055e`** | 新发现 |

证据：`0x055e` 到达的时刻与委托渲染钩子(`TdxW+0x760a80`)的 count 增长**一一对应**（`0x55e` → 数毫秒后 ORDER count+1..3）。

### 13.1 请求格式（发送侧，带股票代码）

```
头部 12B: 0c 03 08 0X YY 01 | 10 00 | 10 00 | CMD(2)
  0x0555/0x055e 的 0X=0a；0x0550/0x0554 的 0X=03
  YY=03 -> 轮询(23B?); YY=02 -> 取数据
payload  : 01 00 | "code"(6B) | seq(u32 LE) | tail(2B)
  tail = 00 00 (轮询) 或 dc 05 (取数据, =1500条)
```
实例：
```
0x0555: 0c0308030a011000100055050100 363033313035 022f0100 0000
0x055e: 0c0308020a01100010005e050100 363033313035 022f0100 dc05
0x0550: 0c03080303011000100050050100 363033313035 29d50000 0000
0x0554: 0c03080203011000100054050100 363033313035 29d50000 dc05
```
⇒ **可自己构造 `0x055e` + 任意代码**，即"不依赖 UI、指定股取实时委托"在协议层已经打通。

### 13.2 委托数据帧用同一密钥 0x49

`0x055e` 载荷 XOR 0x49 后同样是规整明文（1 条记录约 19B）：
```
CT: 68 69 1f 47 68 69 c3 11 fd 9a 63 6a 69 3a 2a fd c5 b5 6a
PT: 21 20 56 0e 21 20 8a 58 b4 d3 2a 23 20 73 63 b4 8c fc 23
对应委托记录: px=8.64 sh=300 typ=0 act=B num=21058280
```
明文逐字节相关（13 个单记录样本）：
```
pt0=0x21 pt1=0x20 pt2(tracks num) pt3=0x0e pt4=0x21 pt5=0x20 pt6(sec?) pt7=0x58 pt8/9 pt10=0x2a pt11.. pt18
```
⇒ 布局与成交类似但字段位置不同，仍是 `字段 ⊕ 0x49`，只需再定 price/num 的定点格式。

### 13.3 结论

**"实时委托能否得到" —— 能。** 协议层已定位：`0x0555`(轮询)/`0x055e`(数据)，请求含股票代码、可自定义。
剩余工作：①补 price/num 数值格式（同成交的定点问题）；②用 FRIDA 的 `WSASend` 在客户端已建连的 socket 上注入自定义 `0x055e` 请求，实现"不改 UI、任意股"。
